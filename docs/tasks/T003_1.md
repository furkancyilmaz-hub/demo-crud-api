# T03_1 — Test verisi dağılımının heterojenleştirilmesi

Feature: [SP003](../features/SP003.md) · Repo: demo-api

## Sorun

T003_0 sonrası veri kümesi doğru büyüklükte ama **tamamen homojen**:

```sql
SELECT proposal_id, count(*) FROM customer
GROUP BY proposal_id HAVING count(*) <> 40;   -- 0 satır: her başvuruda tam 40 müşteri

SELECT customer_id, count(*) FROM payment
GROUP BY customer_id HAVING count(*) > 4;     -- 0 satır: her müşteride 2-4 ödeme
```

Kaynağı seed dosyasındaki iki ifade: `proposal_id = min(id) + (g % 5000)` ve
`generate_series(1, 2 + (c.id % 3))`.

Sonuç: hangi başvuruyu seçersen seç aynı N+1 profilini görüyorsun — child sorgu
sayısı her zaman 40, her ödeme listesi 2-4 satır. Ağır/hafif kayıt ayrımı yok,
uç vaka yok. Bu haliyle veri "performans problemi hissedilsin" isterini
karşılamıyor.

## Adımlar

1. Toplam satır sayıları **değişmeyecek**: 5.000 / 200.000 / 600.000.
   Değişen tek şey bu satırların ebeveynlere dağılımı.

2. Determinizm korunacak (`random()` yok). Bunun için sıra numarasından
   bijektif bir anahtar türet:

   ```
   rn = id - (SELECT min(id) FROM <tablo>) + 1
   t  = 1 + ((rn * <asal>) % <toplam>)
   ```

   `gcd(asal, toplam) = 1` olduğundan `t`, `1..toplam` aralığının bir
   permütasyonudur → her satırda benzersiz, kademe boyutları tam hesaplanabilir
   ve ağır kayıtlar tabloya yayılır. Sabitler: proposal `1103`, customer `7919`.

3. **customer** — başvuru başına 0-500 müşteri (`t = 1 + (rn * 1103) % 5000`):

   | t ≤ | başvuru | müşteri/başvuru | toplam |
   |---|---|---|---|
   | 10 | 10 | 500 | 5.000 |
   | 50 | 40 | 300 | 12.000 |
   | 200 | 150 | 200 | 30.000 |
   | 600 | 400 | 130 | 52.000 |
   | 1.400 | 800 | 60 | 48.000 |
   | 2.600 | 1.200 | 31 | 37.200 |
   | 4.100 | 1.500 | 10 | 15.000 |
   | 4.900 | 800 | 1 | 800 |
   | — | 100 | **0** | 0 |
   | | **5.000** | | **200.000** |

4. **payment** — müşteri başına 0-500 ödeme (`t = 1 + (rn * 7919) % 200000`):

   | t ≤ | müşteri | ödeme/müşteri | toplam |
   |---|---|---|---|
   | 10 | 10 | 500 | 5.000 |
   | 50 | 40 | 150 | 6.000 |
   | 400 | 350 | 60 | 21.000 |
   | 4.000 | 3.600 | 10 | 36.000 |
   | 32.000 | 28.000 | 1 | 28.000 |
   | 89.000 | 57.000 | 2 | 114.000 |
   | 159.000 | 70.000 | 3 | 210.000 |
   | 195.000 | 36.000 | 5 | 180.000 |
   | — | 5.000 | **0** | 0 |
   | | **200.000** | | **600.000** |

5. `due_date`'i 18 aylık pencereye sar: `(((n - 1) % 18) * 30)`. `n` artık 500'e
   kadar çıkıyor; sarma olmadan son vade 2066'ya taşar ve `PENDING` eşiği
   (`2026-08-01`) anlamsızlaşır. Tarih ifadesi bir `LATERAL` içinde bir kez
   hesaplanıp hem kolonda hem status `CASE`'inde kullanılır.

6. `proposal` INSERT'i, `ref` dizileri (isim/soyisim/81 il), `amount` formülü ve
   sondaki `ANALYZE` blokları **aynen kalır**.

## Doğrulama

```sql
SELECT count(*) FROM proposal;   -- 5000
SELECT count(*) FROM customer;   -- 200000
SELECT count(*) FROM payment;    -- 600000

SELECT cnt, count(*) FROM (
  SELECT p.id, count(c.id) cnt FROM proposal p
  LEFT JOIN customer c ON c.proposal_id = p.id GROUP BY p.id) x
GROUP BY cnt ORDER BY cnt;
-- 0→100, 1→800, 10→1500, 31→1200, 60→800, 130→400, 200→150, 300→40, 500→10

SELECT cnt, count(*) FROM (
  SELECT c.id, count(pm.id) cnt FROM customer c
  LEFT JOIN payment pm ON pm.customer_id = c.id GROUP BY c.id) x
GROUP BY cnt ORDER BY cnt;
-- 0→5000, 1→28000, 2→57000, 3→70000, 5→36000, 10→3600, 60→350, 150→40, 500→10

-- F09 regresyonu — bozulmamalı
SELECT count(*) FROM customer WHERE city = 'Ankara';   -- ~2470 (%1,24)
SELECT count(DISTINCT city) FROM customer;             -- 81
EXPLAIN (ANALYZE) SELECT * FROM customer WHERE city = 'Ankara';   -- Seq Scan
```

`docker compose down -v && docker compose up -d` → aynı sonuç.

## Tuzaklar

- **Array subscript `int` olmalı.** `row_number()` bigint döner, `bigint`
  subscript hata verir → `cities[(1 + (rn % 81))::int]`. T003_0'daki
  `date + bigint` tuzağının aynısı.
- **Şehir GLOBAL sıradan türetilmeli.** `city`'yi başvuru içi lokal `n`'den
  hesaplarsan 500 müşterili başvurular il dağılımını bozar, tek il sorgusu
  %2'yi aşar ve F09 çöker. Bu yüzden expand edilen kümeye
  `row_number() OVER (ORDER BY id, n)` ile global `rn` verilir; `identity_no`
  ve `full_name` de bu `rn`'den üretilir.
- `generate_series(1, 0)` sıfır satır döner — 0'lı kademeler için ekstra filtre
  gerekmez.
- `min(id)` ofset düzeltmesi korunmalı; sequence 1'den başlamayabilir.
- SQL'de `%` önceliği `+`'dan yüksek: `1 + (rn * 1103) % 5000` doğru şekilde
  `1 + ((rn * 1103) % 5000)` olarak değerlendirilir.
