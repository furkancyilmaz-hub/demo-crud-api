# T006_0 — Log sorgulama servisi

Feature: [SP006](../features/SP006.md) · Repo: demo-api

## Adımlar

1. `internal/InternalLogController` — `GET /internal/logs`
2. Parametreler: `correlationId` (zorunlu), `minLevel` (opsiyonel),
   `limit` (varsayılan 100, üst sınır 500).
3. Sorgu `(correlation_id, timestamp)` index'ini kullansın, zaman sırasında dönsün.
4. Response `record` DTO listesi.
5. `limit` üst sınırı aşarsa sessizce kırp veya 400 dön — hangisi olduğu belli olsun.

## Doğrulama

```bash
curl "localhost:8080/internal/logs?correlationId=$CID&limit=10"
curl "localhost:8080/internal/logs?correlationId=$CID&minLevel=WARN"
curl "localhost:8080/internal/logs?correlationId=$CID&limit=99999"   # sınır çalışıyor mu
```

## Kararlar

- `limit` üst sınırı (500) aşılırsa veya `<=0` verilirse: **400 Bad Request**
  (sessiz kırpma yok). `@Validated` + `@Min(1) @Max(500)` ile controller
  seviyesinde uygulanıyor.
- Sıralama: `ORDER BY timestamp ASC, id ASC`. `timestamp` milisaniye
  hassasiyetinde olsa da aynı `correlation_id`'ye ait iki satır teorik olarak
  aynı milisaniyeye düşebilir; `id` (`BIGSERIAL`, yazılış sırasıyla monoton)
  ikincil sıralama anahtarı olarak eklendi, deterministik sıralamayı veri
  kaybı olmadan garanti ediyor. Şema/index değişikliği yapılmadı.
- `minLevel` semantiği: minimum seviye eşiği (örn. `WARN` → `WARN` ve `ERROR`
  döner), tam eşleşme değil.
- Response DTO'sunda (`LogEntryResponse`) `id` ve `correlationId` alanları
  bilinçli olarak dışarıda bırakıldı — `correlationId` zaten filtre olarak
  verildiği için her satırda tekrarı gereksiz token maliyeti.
