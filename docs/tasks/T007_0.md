# T007_0 — Sorgu planı servisi

Feature: [SP007](../features/SP007.md) · Repo: demo-api

## Adımlar

1. `internal/InternalExplainController` — `POST /internal/explain`, gövdede SQL.
2. **Girdi kontrolü (önce bunu yaz):**
  - Trim edilmiş sorgu `SELECT` veya `WITH` ile başlamalı
  - `;` içeremez (çoklu ifade engeli)
  - Yasaklı anahtar kelimeler: INSERT/UPDATE/DELETE/DROP/ALTER/CREATE/TRUNCATE/GRANT/COPY
  - İhlalde 400, açıklayıcı mesaj
3. `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON) <sql>` çalıştır.
4. Bağlantıda statement timeout: `SET LOCAL statement_timeout = '5s'`.
5. Dönen JSON'u olduğu gibi ilet — agent üzerinde akıl yürütecek.
6. İşlemi read-only transaction içinde çalıştır.

## Doğrulama

```bash
curl -X POST localhost:8080/internal/explain -d "SELECT * FROM customer WHERE city='Ankara'"
curl -X POST localhost:8080/internal/explain -d "DROP TABLE customer"          # 400
curl -X POST localhost:8080/internal/explain -d "SELECT 1; DROP TABLE customer" # 400
```

## Tuzaklar

- `ANALYZE` sorguyu **gerçekten çalıştırır**. Girdi kontrolü kozmetik değil.
- Kontrolü çağırana bırakma; agent'ın prompt'una güvenme.

## Kararlar

- `ExplainService` `JdbcTemplate` enjekte ediyor. Yeni bir Maven bağımlılığı
  **eklenmedi**: `spring-boot-starter-data-jpa`, `spring-boot-starter-jdbc`'yi
  (ve onun autoconfiguration'ını) `compile` scope'ta transitive olarak zaten
  getiriyor, dolayısıyla `JdbcTemplate` bean'i pom.xml'e dokunmadan otomatik
  konfigüre ediliyor (`mvn dependency:tree` ile doğrulandı). İlk versiyon
  bunu yanlış bilip `DataSource` + `DataSourceUtils.getConnection`/
  `releaseConnection` ile elle JDBC yazmıştı; `JdbcTemplate`'e geçildi çünkü
  `Connection`/`Statement`/`ResultSet` açma-kapama boilerplate'ini kaldırıyor
  ve `SQLException`'ı Spring'in standart `DataAccessException` hiyerarşisine
  çeviriyor. `JdbcTemplate` de aynı şekilde `@Transactional(readOnly = true)`
  altında `JpaTransactionManager`'ın açtığı fiziksel JDBC bağlantısını
  paylaşıyor (kendi içinde yine `DataSourceUtils` kullanıyor). Hibernate'in
  `readOnly` altında bağlantıyı erken açıp `setReadOnly(true)` çağırması,
  Postgres tarafında `SET TRANSACTION READ ONLY` olarak da işliyor —
  uygulama seviyesindeki girdi kontrolünün yanında ikinci bir DB seviyesi
  güvenlik katmanı, onun yerine geçmiyor.
- Girdi kontrolü tamamen `ExplainService` içinde, çağırana (controller'a)
  güvenilmiyor: boş/`SELECT`|`WITH` ile başlamıyor/`;` içeriyor/yasaklı
  anahtar kelime (`\b(...)\b`, case-insensitive regex — `created_at` gibi
  alan adlarında yanlış pozitif üretmesin diye kelime sınırı kullanıldı).
  İhlalde `InvalidExplainQueryException` → `GlobalExceptionHandler`'da ayrı
  bir handler ile 400 (mevcut `handleInvalidReference`/`handleConflict`
  gruplarına eklenmedi; onlar aynı domain kavramını paylaşıyor, bu ise farklı
  bir güvenlik sınırı).
- `SET LOCAL statement_timeout = '5s'` uzun süren sorguyu Postgres seviyesinde
  kesiyor; timeout'tan doğan hata özel olarak ele alınmadı, `JdbcTemplate`
  bunu otomatik olarak unchecked `DataAccessException`'a çevirip mevcut genel
  500 handler'ına düşürüyor — kabul kriteri yalnızca sorgunun kesilmesini
  istiyor, özel bir status kodu istemiyor.
- Dönen `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` çıktısı (`QUERY PLAN`
  kolonu, tek satır) hiç parse edilmeden `ResponseEntity<String>` ile
  `Content-Type: application/json` olarak aynen iletiliyor.
- Testcontainers eklenmedi (repo'da hiç yok). JDBC etkileşimi
  (`ExplainServiceTest`) mock `JdbcTemplate` ile doğrulanıyor; gerçek Postgres
  round-trip'i (gerçek plan JSON şekli, gerçek timeout iptali) bu task'ın
  kendi Doğrulama bölümündeki curl komutlarıyla manuel teyit edildi (bkz.
  aşağıdaki not — bu teyit sırasında gerçek bir hata bulundu ve düzeltildi).
- **Bulgu:** İlk versiyon `@RequestBody String sql` kullanıyordu. `curl -d`
  varsayılan olarak `Content-Type: application/x-www-form-urlencoded` yolluyor;
  bu content-type ile Spring MVC gövdeyi olduğu gibi değil, form-decode edip
  yeniden kodluyor (`"SELECT 1"` → `"SELECT+1="` gibi bozuk bir metne
  dönüşüyor), bu da Postgres'te sözdizimi hatasına yol açıyordu — yalnızca
  `curl -H "Content-Type: text/plain"` ile doğru çalışıyordu. Task'ın kendi
  doğrulama komutları content-type başlığı vermediği için bu gerçek bir
  regresyondu, curl ile manuel test edilmeden fark edilmezdi. Çözüm: controller
  artık `HttpServletRequest.getInputStream()`'i doğrudan okuyor
  (`StreamUtils.copyToString`), content-type'tan bağımsız olarak ham gövdeyi
  değiştirmeden alıyor.
