# T0012_0 — Ek ister: şema metadata ucu

Feature: [SP0012](../features/SP0012.md) · Repo: demo-api

## Adımlar

1. `GET /internal/schema/foreign-keys`
2. Kaynak: `DatabaseMetaData.getImportedKeys(...)` ya da eşdeğer bir
   `information_schema` sorgusu. Kodda sabit liste tutma.
3. Cevap:
   ```json
   [
     { "childTable":"customer", "childColumn":"proposal_id",
       "parentTable":"proposal", "parentColumn":"id" },
     { "childTable":"payment", "childColumn":"customer_id",
       "parentTable":"customer", "parentColumn":"id" }
   ]
   ```
4. Tablo ve kolon adları küçük harf dönsün.
5. Yalnızca uygulama şemasını dön; `app_log` gibi altyapı tablolarını filtrele.
6. Salt okunur; parametre almasın.

## Doğrulama

```bash
curl localhost:8080/internal/schema/foreign-keys
```
- İki ilişki dönüyor
- Şemaya yeni bir FK ekleyip `down -v` sonrası listede göründüğünü doğrula

## Kararlar

- **Metadata kaynağı:** JDBC `DatabaseMetaData` — `getTables(...)` ile tabloları say,
  sonra tablo başına `getImportedKeys(...)`. `getImportedKeys` JDBC sözleşmesinde
  tablo adını nullable saymıyor; pgjdbc `null` tabloyu fiilen kabul ediyor ve tek
  round trip'te cevap veriyor, ama bu sürücüye özgü, sözleşmeye dayanmayan bir
  davranış — sürücü yükseltmesi kırabilir. 4 tabloda döngü bedava, o yüzden
  sözleşmeye uygun yol seçildi.
- **Reddedilenler:** `information_schema.constraint_column_usage` (ordinal
  taşımadığı için composite FK kolonlarını yanlış eşler), `pg_catalog.pg_constraint`
  (elle yazılmış Postgres-only katalog SQL'i, sürücünün zaten yaptığı işi
  tekrarlıyor), JPA metamodel / `@JoinColumn` yansıması (canlı şemayı değil entity
  eşlemesini okur — kabul kriterini doğrudan ihlal eder).
- **Cache yok:** `@Cacheable` veya lazy-init alan "şema değişirse liste kendiliğinden
  güncellenir" kriterini ihlal ederdi. Her çağrı 1+N metadata sorgusu yapıyor;
  internal uç ve 4 tablo için önemsiz.
- **Katmanlar:** `ForeignKeyMetadataRepository` (`@Repository`, concrete class) JDBC
  erişimini izole eder ve DB'nin bildirdiği satırları ham döner;
  `SchemaMetadataService` küçültme + filtre + sıralama yapar. Repository'nin Spring
  Data arayüzü olma zorunluluğu yok — CLAUDE.md katmanı sorumlulukla tanımlıyor.
  Bu ayrım aynı zamanda test sınırı: mantığın tamamı DB'siz test edilebiliyor.
- **Bağlantı:** `JdbcTemplate.execute(ConnectionCallback)`. Bağlantıyı
  `DataSourceUtils` üzerinden alır (servisin `readOnly` işlemine katılır, ikinci
  bağlantı açmaz), serbest bırakmayı garanti eder, `SQLException`'ı
  `DataAccessException`'a çevirir. `DbLogAppender`'ın raw `dataSource.getConnection()`
  deseni kullanılmadı — o sınıf Spring yaşam döngüsü dışında olmak zorunda.
- **Şema çözümü:** `connection.getSchema()`, null/blank ise `"public"`. Fallback
  dekoratif değil: `getSchema()` nullable ve yalnızca `search_path`'in ilk girdisini
  yansıtır. `getTables`'ın schema argümanı pgjdbc'de LIKE pattern olduğu için dönen
  satırlarda `TABLE_SCHEM` eşitliği ayrıca kontrol ediliyor; `PKTABLE_SCHEM` farklı
  olan satırlar atılıyor (cross-schema FK uygulama şeması dışı bir tabloyu sızdırırdı).
- **Altyapı filtresi config'te:** `schema-metadata.excluded-tables` (tipli
  `@ConfigurationProperties`, `@DefaultValue("app_log")`). Yasaklanan şey FK
  listesinin sabitlenmesi; hangi tablonun altyapı sayıldığı politika girdisi.
  `@ConfigurationPropertiesScan` eklendi (record properties `@Component` değil).
  Yaml'daki harf durumu önemsiz — dışlama adları da küçültülerek karşılaştırılıyor.
- **`Locale.ROOT` zorunlu:** JVM default locale `tr-TR`; çıplak `toLowerCase()`
  `"ID"` → `"ıd"` (noktasız i) üretip `ID` / `IDENTITY_NO` gibi tanımlayıcıları
  sessizce bozardı. Regresyon testi var.
- **Sıralama:** `childTable` → `constraintName` → `keySequence`. pgjdbc'nin kendi
  sırası **parent** tabloya göre, yani sıralamasız bırakılsa `payment→customer` önce
  gelir ve spec örneğiyle uyuşmazdı. `childColumn` ile sıralama composite FK'nin
  kolon sırasını bozardı.
- **Composite FK:** kolon çifti başına bir JSON nesnesi. Spec'in düz şekli bunu
  gerektiriyor; constraint adı cevaba konmadı, dolayısıyla tüketici "bir composite
  FK" ile "iki bağımsız tek-kolonlu FK"yi ayırt edemez. Bu şemada composite FK yok.
- **Sayfalama yok — bilinçli:** CLAUDE.md'nin "listeler her zaman sayfalanır" kuralı
  domain verisi için. FK kümesi şemayla sınırlı ve sayfalamak ucun amacını bozar
  (analiz agent'ı tam grafı istiyor).
- **Hata yönetimi:** `GlobalExceptionHandler`'a dokunulmadı. DB hatası
  `DataAccessException` olarak mevcut catch-all'a düşüyor → 500 + "An unexpected
  error occurred"; SQL/sınıf adı sızmıyor. Ayrı 503 eşlemesi eklenmedi.
- **Test:** servis (7 test) ve controller (2 test) mock ile. `DatabaseMetaData` /
  `ResultSet` **mocklanmadı** — kendi yazılan stub'lar doğrulanmış olurdu ve pgjdbc
  sözleşmesi test içinde yeniden yazılırdı. Repository için otomatik test yok
  (Testcontainers yeni bağımlılık olurdu); canlı doğrulama aşağıda.
- **Doğrulama şekli:** `01-schema.sql` + `down -v` yerine çalışan DB'ye
  `ALTER TABLE ... ADD CONSTRAINT ... NOT VALID` ile iki geçici FK eklenip
  curl'lendi, sonra düşürüldü — 200k satırlık seed'i iki kez yeniden üretmeye gerek
  kalmadı ve kanıt daha güçlü oldu: `customer.id → proposal.id` **uygulama yeniden
  başlatılmadan** listede göründü (liste canlı ve cache'siz), `app_log.id →
  proposal.id` ise görünmedi (filtre canlı DB'de de çalışıyor — `app_log`'un normalde
  hiç FK'si olmadığı için bu tek gözlemlenebilir kanıt).
